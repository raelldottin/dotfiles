Declarative workstation configuration for macOS and Linux using Nix, Home Manager, nix-darwin, and nix-homebrew.

## Migration Status

The Nix migration is currently staged on `dev`.

- `main` remains the pre-Nix stable configuration.
- `dev` contains the Nix/Home Manager migration.
- CI validates the flake, Linux Home Manager output, and Apple Silicon nix-darwin output.
- The legacy shell/Python installer remains available as a rollback path.
- Promotion from `dev` to `main` is gated on a successful activation on the real Mac.

This keeps the migration reversible while changing the system that manages the workstation itself.

## macOS

The macOS configuration targets Apple Silicon and is exposed as:

```text
.#macbook
```

### First Activation

Use the `dev` branch while the migration is being validated:

```bash
git switch dev
git pull

nix flake check

sudo nix run nix-darwin/nix-darwin-26.05#darwin-rebuild -- \
  switch --flake .#macbook
```

During the first activation, Home Manager backs up conflicting managed files using the `.hm-backup` suffix.

The migration intentionally does not remove unlisted Homebrew software. Existing formulae and casks remain in place while the Nix configuration is proven on the workstation.

### Normal Rebuild

After nix-darwin is installed:

```bash
sudo darwin-rebuild switch --flake .#macbook
```

### Update Pinned Inputs

```bash

nix flake check
sudo darwin-rebuild switch --flake .#macbook
```

Review `flake.lock` before committing an input update.

## Day-to-Day Configuration Workflow

The repository is the source of truth. Prefer changing the declarative configuration first and then rebuilding the workstation from it.

The normal direction is:

```text
Git repository
      ↓
Nix / Home Manager
      ↓
workstation
```

Avoid treating the workstation as the authoritative copy of managed configuration.

### Start a Change

Update `dev`, then create a short-lived branch:

```bash
git switch dev
git pull
git switch -c config/<change-name>
```

Use a focused branch name such as:

```text
config/tmux-copy-mode
config/add-ripgrep
config/add-vscode
config/nvim-lsp
```

### Edit the Source, Not the Generated File

Common changes belong in these locations:

| Change | Edit |
| --- | --- |
| CLI/development package | `nix/home.nix` |
| zsh configuration | `nix/home.nix` |
| tmux configuration/plugins | `nix/home.nix` |
| Neovim configuration | `config/nvim/` |
| macOS/Homebrew cask | `nix/darwin.nix` |
| Nix inputs | `flake.nix` and generated `flake.lock` |
| README content | `README.template` |

For files owned by Home Manager, edit the repository source rather than the installed path in `$HOME`. For example, change `config/nvim/` instead of directly modifying `~/.config/nvim/`.

### Validate Before Rebuilding

```bash
nix flake check
```

For a formatting pass:

```bash
nix fmt
nix flake check
```

During the migration, the legacy repository checks remain useful as an additional regression gate:

```bash
make verify
```

### Apply the Change to macOS

```bash
sudo darwin-rebuild switch --flake .#macbook
```

Test the affected tools after the rebuild. For shell or terminal changes, start a fresh shell and tmux session rather than relying only on the current process.

If the configuration needs another adjustment, edit the repository again and rerun the rebuild. Do not commit a configuration that has only passed static evaluation but has not been exercised on the workstation when the change affects runtime behavior.

### Review and Commit

```bash
git status
git diff
git diff --check

git add <changed-files>
git commit -m "Configure <change>"
git push -u origin HEAD
```

Review `flake.lock` carefully whenever it changes. A package/configuration edit should not unexpectedly rewrite input revisions.

Open a pull request from the change branch into `dev`. After CI passes, merge it into `dev`.

During the migration the promotion path is:

```text
config/* or feature branch
          ↓
         dev
          ↓
real workstation validation
          ↓
         main
```

Once Nix is fully promoted, `main` becomes the stable workstation definition.

## Adding Software

### CLI or Development Tools

Prefer nixpkgs for command-line and development tools.

Add the package to `home.packages` in `nix/home.nix`:

```nix
home.packages = with pkgs; [
  jq
  ripgrep
];
```

Then validate and rebuild:

```bash
nix flake check
sudo darwin-rebuild switch --flake .#macbook
```

### macOS GUI Applications

GUI applications that are intentionally kept in Homebrew belong in the cask list in `nix/darwin.nix`:

```nix
homebrew.casks = [
  "rectangle"
  "visual-studio-code"
];
```

Then rebuild with the same `darwin-rebuild` command.

## Reconciling Manual Host Changes

Nix does not automatically export workstation changes back into Git.

If software or configuration is changed directly on the host, decide whether that change should be permanent. If it should, translate it into the appropriate repository configuration and rebuild.

For example, after a manual:

```bash
brew install --cask visual-studio-code
```

add the cask to `nix/darwin.nix`, run `nix flake check`, rebuild, and commit the declarative change.

The same rule applies to manually installed CLI tools, shell changes, tmux changes, and managed dotfiles. A manual host change is temporary until it is represented in the repository.

Before pushing a workstation change, this is a useful audit sequence:

```bash
git status
git diff
nix flake check
sudo darwin-rebuild switch --flake .#macbook
```

Then verify the affected behavior and commit the source configuration.

## Homebrew Strategy

Homebrew is not being removed.

It remains useful for macOS GUI software while command-line and development tooling moves toward nixpkgs. The current migration uses:

```nix
homebrew.onActivation.cleanup = "none";
```

That prevents the first activation from deleting Homebrew software that has not yet been classified into the Nix configuration.

Once the migration is proven, the remaining Homebrew inventory can be reviewed and either moved into Nix, retained as a cask, or removed.

The legacy installer remains available until the Nix configuration has been activated successfully on the workstation.

```bash

```

Do not delete the legacy installer, its package inventories, or its compatibility tests until the macOS activation has been verified.

## Migration Completion Criteria

The migration can move from `dev` to `main` after:

1. `darwin-rebuild switch --flake .#macbook` succeeds on the real Mac.
2. zsh starts normally.
3. tmux loads its expected plugins and bindings.
4. Neovim starts with the existing configuration.
5. expected CLI development tools are available.
6. Homebrew GUI applications remain intact.
7. a second rebuild completes cleanly and demonstrates idempotence.

After that, the legacy shell/Python installer and obsolete package inventory files can be removed in a separate cleanup change.
